Problem

Support document upload and processing behind authenticated APIs, while making relevant document content available through search and chat.

My approach

Separated authentication, document handling and the API gateway; connected services through REST and paired storage with cache and queued background work.

What I learned

How service boundaries, independently verified tokens, shared infrastructure and asynchronous processing fit together in a containerised backend.

High-level system architecture

REQUEST → SERVICES → DATA / QUEUE → WORKERS

High-level illustration based on the resume description, not a verified deployment topology. The technical rationales below explain the standard tradeoffs implied by the selected components; confirm the exact service-to-database and worker-to-LLM calls against the repository before presenting them as verified implementation details.

Architecture & communication

The API gateway routes requests to the authentication and document-handling services over REST. PostgreSQL is used for storage, Redis for caching, session storage and rate limiting, and RabbitMQ with Celery for background task queuing and processing. The project also includes a document search-and-chat module that retrieves relevant content and generates LLM responses.

Key technical decisions

JWT authentication: services can verify issued tokens independently instead of depending on a central authentication lookup for every request.
Redis: one shared in-memory layer supports the stated caching, session-storage and rate-limiting use cases.
Celery + RabbitMQ: queue document-processing work for workers rather than keeping all processing inside the request path.

What I learned

How to divide backend responsibilities across services, apply stateless token verification, use cache and messaging infrastructure, and package a multi-service application consistently with Docker Compose.
